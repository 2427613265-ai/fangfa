# 权利要求书撰写

基于交底理解稿或用户提供的技术方案，撰写**方法类**权利要求书。默认输出中文权利要求文本；需要时附简要起草说明（不替代权利要求正文）。

## 何时使用

- 用户要求撰写、修改、拆分或合并权利要求
- 已完成交底理解，进入「写权项」阶段
- 用户给出实施例/说明书，需要反推或对齐权利要求

## 开始前确认

若上下文中尚无结构化理解，先做最小确认（或建议先跑 `understand-disclosure`）：

1. 方法主题名称
2. 必要步骤（最小可实施集合）
3. 优选参数、附加步骤、可选工况
4. 最接近现有技术差异点
5. 用户倾向：保护范围偏宽 / 偏稳妥

信息不足时提问；禁止用虚构步骤凑独权。

## 起草流程

1. **定独权骨架**：主题名称 + 必要步骤特征；只保留完成发明所必需的技术特征。
2. **写独立权利要求**：方法步骤清楚、顺序/条件关系明确；避免纯效果、纯原理限定。
3. **布置从属权利要求**：参数范围、优选材料/设备、附加步骤、适用场景等分层展开。
4. **自检**：对照下方检查项，再输出。

## 写作规范

### 独立权利要求

- 格式示例：`1. 一种……的方法，其特征在于，包括以下步骤：`
- 步骤用（1）（2）（3）或 S1/S2 等稳定编号，全文一致。
- 必要参数可写入独权；不确定的优选值放入从权。
- 不把商业效果、抽象目的写成特征。

### 从属权利要求

- `根据权利要求X所述的方法，其特征在于，……`
- 每条只增加一层清楚限定；避免堆砌无关特征。
- 引用关系简单清晰；非用户明确要求，不做复杂的多引多。

### 用语

- 与交底/说明书用语保持一致（同一对象不要多名）。
- 中性、准确；不出现「显著」「大幅」等空泛词作为特征。
- 缺数据处标 `【待补充：参数/范围】`，勿编造数值。

## 输出格式

默认按专利权项列表输出：

```text
1. 一种……的方法，其特征在于，包括以下步骤：
（1）……；
（2）……；
（3）……。

2. 根据权利要求1所述的方法，其特征在于，……。

3. 根据权利要求1或2所述的方法，其特征在于，……。
```

正文后附（简短）：

- **保护思路**：独权抓什么、从权如何分层
- **待确认**：可能影响授权/范围的歧义点
- **未写入权项但说明书应支撑的内容**（如有）

## 修改权项时

- 先说明改动意图（扩大/限缩/澄清/应对对比文件）
- 给出修改后的完整权项文本，不要只给零散替换句
- 指出对说明书实施例是否需要对齐修改
