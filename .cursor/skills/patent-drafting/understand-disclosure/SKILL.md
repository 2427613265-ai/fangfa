# 交底书理解

把发明人交底先**查能否成立**，再按固定顺序帮用户（专利撰写人）把方案吃准。本步的读者是用户本人，不是先填一张给机器用的表。

只做检查与理解。不写权利要求、不写说明书章节、不把部件名称定稿（正式命名交给 `name-components`）。

## 何时启用

- `/draft-patent` 的第一步
- 用户要求理解交底、梳理技术方案、看方案能不能跑通
- 即将写权利要求，但还没有理解稿

无交底材料时先要材料，不编造技术方案。

## 必须遵守的顺序

按下面顺序做、按下面顺序讲。不要先讲方案再补问题，不要没解释名词就拆模块，不要没串工作流程就谈效果。

1. **跑通检查**（理解之前）
2. **技术问题**（领域陌生或名词密集时，先解释名词再把问题讲清）
3. **技术方案**（名词清楚之后：方法分步骤；结构分功能/模块）
4. **整体工作流程**
5. **技术效果**
6. **给下游的沉淀**（理解完成后再写，不要提前用权项思维打断理解）

跑通检查未结束前，不要进入第 2 步及以后。

---

## 1. 跑通检查（理解之前）

先当审稿人，不当撰写人。问三件事：逻辑上自洽吗？物理/工程上成立吗？按交底把方案走一遍，能不能跑通？

### 查什么

- **逻辑问题**：前后矛盾；问题与方案对不上；缺关键因果；步骤顺序说不通；同一对象前后角色冲突；条件互斥却被写成同时成立。
- **物理 / 工程错误**：违背基本物理或该领域常识（运动、力、热、电、材料、信号流向、时序、单位等）；结构上装不上、会干涉、传不到；方法上缺必不可少的中间状态。
- **能否跑通**：按交底从起始状态走到结束，中间会不会断。缺了某一步/某个零件就无法实现时，要标出来，不要自行补上发明人没说的关键环节。

### 怎么标

每条问题写清：出处（交底原意）、错在哪里、会怎样卡住。区分：

| 标记 | 含义 |
| --- | --- |
| 交底原文 | 交底写明的 |
| 合理推断 | 专业上顺理成章的补充，必须标明 |
| 交底未写 | 缺失，不得当成已公开内容 |

### 检查结论与是否继续

- **跑不通或有硬伤**（物理上不成立、关键逻辑矛盾）：先把问题摊开，**停在这里**，等用户决定：问发明人、带着问题继续理解、还是先改交底。未得到用户表态前，不进入技术问题与方案理解。
- **存疑**：列出疑点；可以问用户是否继续。用户说继续则往下，疑点留在理解稿里。
- **可跑通**（可附次要瑕疵）：简要给结论，立刻进入第 2 步。

不要为了让方案看起来能写专利，而用推断把窟窿补圆。

---

## 2. 技术问题

方案还没拆之前，先让用户明白：**发明人要解决的是什么问题、在什么场景下、现有做法差在哪**。

讲清这些即可：

- 应用场景与约束（谁、在哪、什么工况）
- 现有做法 / 最接近的常规手段（只根据交底，不编造对比文件）
- 缺陷或痛点（每条最好能被后文方案对上）
- 本发明针对的核心问题（一句话，避免把效果或方案倒装成问题）

问题与后文方案明显对不上，记回第 1 步的逻辑问题，不要在理解阶段圆过去。

### 陌生领域与技术名词（先于拆方案）

交底所属领域用户不熟，或专门名词多、同词不同义时：**先帮用户把名词弄懂，再继续把技术问题讲完，然后才允许进入第 3 步。**

名词解释要求：

- 用该领域的普通话讲清「它是什么、在本交底里指什么、和相邻概念差在哪」
- 优先用交底语境，不堆百科；必要时用一句类比，但类比不能替代定义
- 列出交底里的别称；此处只求**读懂**，不在此选定权利要求用名
- 领域常见、用户显然熟悉的词不要展开

名词表是给用户看的释义，不是 `name-components` 的正式命名表。

---

## 3. 技术方案（分步骤，或分功能 / 模块）

名词已清楚之后，再拆方案。先判断发明类型：`方法` / `结构` / `方法+结构`（拿不准就按交底主线选一种拆法，可并用，不要为分类反复打断用户）。

- **方法为主**：按可执行顺序分步骤。每步写清：对什么对象、做什么动作、关键条件/参数、做到什么算完成、下一步靠什么接上。
- **结构 / 装置 / 系统为主**：按功能或模块拆。每个模块写清：是什么、起什么作用、和谁连接或配合、关键形状/位置/传动或信号关系。
- **方法 + 结构**：先让用户知道「有哪些块、怎么连」，再按使用过程看步骤；或按交底叙述主线，但两套都要能对上。

拆的时候：

- 用交底用词；有歧义就并列写出，留给命名 skill
- 必要手段与锦上添花的优选手段分开记，但本步目的仍是让用户看懂，不是写独权
- 图上有的关系、文字没写的：标明来自附图，仍属交底内容

---

## 4. 整体工作流程

模块或步骤拆完后，用一条连贯过程把方案串起来，让用户在脑子里把整机/全过程走一遍。

写清：从什么状态开始 → 中间如何传递（物料、运动、能量、信号、控制）→ 到什么状态结束；人怎么操作、装置怎么响应；有循环或分支则单独说清。

这里应能回答：「按交底，这个东西到底怎么干活？」若串不起来，回到第 1 步补「跑不通/存疑」，不要用空话带过。

---

## 5. 技术效果

流程清楚之后，再谈效果。效果要能对上第 2 步的问题，并尽量能指回第 3 步的哪一段手段。

- 只写交底给出的效果、对比、数据；没有量化就写「交底未提供量化」
- 区分：交底明确写的效果 / 由手段可合理想到的效果（须标推断）/ 空泛宣传（不当作技术效果）
- 不编造试验数据、不夸大

---

## 6. 给下游的沉淀

上述理解用户能跟上之后，再写入理解稿末尾，供命名和独权使用。不要把本节提前当成讲解主线。

- 发明类型
- 对象清单（部件、步骤、物料、信号等，保留交底叫法，不定稿）
- 必要特征候选 vs 优选/附加特征候选（供独权/从权分流，此处不写权项文句）
- 仍待向发明人确认的问题（含跑通检查遗留）

不要在本 skill 里启用 `reinforce-inventiveness`。用户认为创造性不够或要求补强时再转。

---

## 输出

用中文向用户讲解，顺序与上文第 1–6 步一致。同时落盘 `cases/<案号>/01-understanding.md`（案号未知可用 `draft`），章节与讲解顺序相同：

1. 跑通检查
2. 技术问题（含名词解释，如有）
3. 技术方案（步骤或功能/模块）
4. 整体工作流程
5. 技术效果
6. 给下游的沉淀

讲解以用户看懂为准，可举例、可复述，但关键结论要能对回交底。不要输出权利要求或说明书章节。

## 边界

- 上游：用户交底（文本、图、口头补充）
- 下游必读本理解稿：`name-components`、`write-independent-claim`、`write-dependent-claims`、`write-embodiments`、`write-specification-other`
- 与 `name-components`：本步只释义、列对象；正式权项用名不在此定
