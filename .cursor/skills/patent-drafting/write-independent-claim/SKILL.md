# 独权撰写（架构）

**流水线第 3 步，权利要求书的核心。** 本阶段只定职责与契约，独权撰写细则待补。

## 架构角色

在理解稿给出的必要特征候选上，用命名表中的正式名称，写成一项（或按类型需要的若干项）独立权利要求。保护范围主要由本步决定。

## 何时启用

- 全流程中，理解 + 命名完成之后
- 用户明确要求写 / 改独立权利要求
- 禁止：尚无理解稿时直接写独权（应先启用 `understand-disclosure`）
- 不要因 Agent 自己觉得创造性不够而启用 `reinforce-inventiveness`；用户提出创造性不够或要求补强时再转

## 门禁

- 必须已有 `01-understanding.md`。
- 定稿必须已有 `02-naming.md`；若命名未完成，先启用 `name-components`。
- 不输出从属权利要求（交给 `write-dependent-claims`）。
- 不输出说明书章节。

## 输入 / 输出契约

**输入**

- 理解稿：发明类型、必要特征候选、方案主线
- 若已做过创造性补强：同时读取 `01b-inventiveness-reinforcement.md`（及回写后的理解稿）
- 命名表：正式术语

**输出**（`03-independent-claim.md`）

- 独立权利要求正文
- 所采用的必要特征清单（与理解稿对应关系，格式待补）
- 未写入独权、留给从权/实施例的特征指针（不在本步展开从权文本）

## 上下游

- 上游：`understand-disclosure`、`name-components`
- 下游：`write-dependent-claims`、`write-embodiments`、`write-specification-other`

## 方法 / 结构

架构预留两个分支（规则待补）：

- 方法独权：步骤 + 必要技术条件
- 结构独权：部件 + 连接/位置等必要关系

## 内容待补

- 独权撰写规范、特征取舍、范围宽窄策略
- 前序 + 特征部分的行文格式
- 方法 / 结构各自的独权骨架
- 与理解稿必要特征的对照检查
