# 交底书创造性补强（架构）

**可选 skill，不在默认流水线中。** 本阶段只定职责与契约，补强方法待补。

## 架构角色

在用户已经认为方案创造性不够之后，按用户指令对交底/理解稿做创造性方向的补强准备，供后续独权等步骤使用。

创造性够不够**只由用户判断**。本 skill 不代替用户做创造性结论，也不在未受命时提出「建议先补强」。

## 何时启用（唯一条件）

同时满足才启用：

1. 用户已表示自己判断创造性不够（或同等意思）；并且
2. 用户明确要求启动本 skill（`/reinforce-inventiveness`、`启动创造性补强`、`跑创造性补强` 等）。

仅有第 1 点、没有第 2 点：不启用，不追问是否要启动，不把本 skill 插入当前撰写流程。

## 禁止

- 禁止因 Agent 自行评估「创造性弱 / 与现有技术接近」而启用。
- 禁止因用户只是讨论创造性、对比文件、授权前景而启用。
- 禁止 `draft-patent` 全流程自动插入本步。
- 禁止在用户未点名本 skill 时读取本 `SKILL.md` 并按其执行。
- 本 skill **不直接撰写**独权、从权或说明书正文。

## 门禁

- 建议已有理解稿（`01-understanding.md`）；若没有，先说明缺少理解稿，等用户决定是先跑 `understand-disclosure` 还是仍要直接补强。
- 未收到上述「明确启动」指令时，本文件等同不存在。

## 输入 / 输出契约

**输入**

- 用户确认创造性不够的判断（不必展开理由，除非用户要说）
- 理解稿（有则用）及原始交底
- 用户给出的对比点、现有技术线索（有则用）

**输出**（`01b-inventiveness-reinforcement.md`，细目待补）

- 补强后的技术方案要点（供理解稿回写 / 独权重写使用）
- 与原理解稿的差异说明
- 仍待用户确认的项

补强完成后：不自动重跑独权。是否回写理解稿、是否重写权项，等用户指示。

## 上下游

- 默认上游：`understand-disclosure`（可选但推荐）
- 不进入 `draft-patent` 的固定顺序
- 若用户随后要求继续写权项：下游仍是 `name-components` → `write-independent-claim` …；撰写 skill 应改读补强稿（及回写后的理解稿）
