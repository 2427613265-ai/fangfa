# 交底书创造性补强（架构）

**可选 skill，不在默认流水线中。** 本阶段只定职责与契约，补强方法待补。

## 架构角色

用户认为方案创造性不够时，对交底/理解稿做创造性方向的补强准备，供后续独权等步骤使用。

创造性够不够由用户判断，本 skill 不代替用户下结论。

## 何时启用

用户用自然语言表达即可，不必使用斜杠命令，也不必说出 skill 全名。例如：

- 创造性不够、创造性弱、发明点不够、授权有风险，并希望补强
- 补强创造性、强化发明点、把交底往创造性上靠一靠
- `/reinforce-inventiveness`

若用户只说创造性不够、尚未说要不要补强：问一句是否启动本 skill，得到肯定后再做；不要反复追问。

## 不要启用的情形

- 默认 `/draft-patent` 全流程：不要自动插入本步。
- 仅 Agent 自己觉得与现有技术接近、创造性弱：不要自行启用，也不要主动推销本 skill。
- 用户只是在了解现有技术或对比文件，没有补强意向：不要启用。

本 skill **不直接撰写**独权、从权或说明书正文。

## 门禁

- 建议已有理解稿（`01-understanding.md`）；若没有，说明缺少理解稿，由用户选择先跑 `understand-disclosure` 还是直接补强。

## 输入 / 输出契约

**输入**

- 用户对创造性不足的判断或补强意向（不必展开理由，除非用户要说）
- 理解稿（有则用）及原始交底
- 用户给出的对比点、现有技术线索（有则用）

**输出**（`01b-inventiveness-reinforcement.md`，细目待补）

- 补强后的技术方案要点（供理解稿回写 / 独权重写使用）
- 与原理解稿的差异说明
- 仍待用户确认的项

补强完成后：不自动重跑独权。是否回写理解稿、是否重写权项，等用户指示。

## 上下游

- 默认上游：`understand-disclosure`（推荐，非强制）
- 不进入 `draft-patent` 的固定顺序
- 若用户随后要求继续写权项：下游是 `conceive-independent-claim` → `write-claims`（接受独权后先 `name-components`）；撰写 skill 应改读补强稿（及回写后的理解稿）
