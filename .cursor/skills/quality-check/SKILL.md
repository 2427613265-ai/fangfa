# 质检

对方法撰写产物做结构化质检，输出问题清单与修改建议。默认**只质检、不擅自大改全文**；若用户要求「质检并直接修订」，再给出修订稿。

## 何时使用

- 用户说质检、校对、挑错、审查、交付前检查
- 同时存在交底理解 / 权利要求 / 说明书，需要互一致性检查
- 对单份权项或说明书做可实施性与撰写规范检查

## 质检对象

根据用户指定或上下文自动识别：

| 对象 | 说明 |
| --- | --- |
| 交底理解稿 | 来自 `understand-disclosure` |
| 权利要求书 | 来自 `write-claims` |
| 说明书 | 来自 `write-specification` |
| 组合稿 | 以上多份一起互校 |

对象不清时先问要检哪些文件。

## 质检维度

### A. 完整性

- 必要章节/权项是否齐全
- 步骤链是否可从头执行到尾
- 关键参数、材料、设备是否缺失

### B. 一致性

- 交底 ↔ 权项 ↔ 说明书：主题、步骤、术语是否统一
- 独权特征是否均被实施例支撑
- 有益效果是否回扣背景问题与技术特征

### C. 可实施性

- 本领域人员能否据此再现
- 是否仅有功能描述而无操作步骤
- 条件分支、先后顺序是否清楚

### D. 权项质量（若有）

- 独权是否为最小必要特征集（过宽/过窄）
- 从权分层是否合理、引用是否清晰
- 是否把效果/原理误写入特征

### E. 风险与合规表达

- 有无编造数据、规范号、对比文件
- 有无空泛断言、宣传语
- 待补充项是否已标出

## 输出格式

```markdown
# 质检报告

## 结论
- 总体：通过 / 有条件通过 / 不通过
- 一句话原因

## 问题清单（按严重级别）
### 阻断（必须改）
1. 【位置】问题 …｜建议 …

### 重要（强烈建议改）
1. …

### 建议（可选优化）
1. …

## 一致性对照（多稿时）
| 检查项 | 交底 | 权项 | 说明书 | 结果 |
| --- | --- | --- | --- | --- |

## 待补充清单
- …

## 建议的下一步
- 回到哪个 skill 修改（understand-disclosure / write-claims / write-specification）
```

## 原则

- 先列问题再给建议，避免只给空洞印象分。
- 区分「交底原文如此」与「撰写引入的问题」。
- 不因追求完美而改动用户未授权的保护策略；策略分歧单独列出供确认。
- 无足够文稿时，说明无法质检的部分，不要假装已检。

## 衔接

- 发现问题后：交底不清 → `understand-disclosure`；权项问题 → `write-claims`；说明书问题 → `write-specification`
